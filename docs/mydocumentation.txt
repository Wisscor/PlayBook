I checked the backend realtime system and the frontend messaging UI. The backend is prepared for realtime messaging, but the frontend is still using mock data and is not connected yet.

Current backend implementation
The backend has two communication methods:

1. HTTP API
The frontend should use HTTP for loading existing data and creating conversations.

Available endpoints:
POST /realtime/conversations
GET  /realtime/conversations
GET  /realtime/conversations/{conversation_id}/messages
GET  /realtime/notifications
POST /realtime/notifications/read
These endpoints are implemented in rest.py.

Conversation creation
POST /realtime/conversations
Body:

{
  "peer_id": "user-uuid"
}

Important backend rule:

A conversation can only be started if both users follow each other.

If the conversation already exists, the existing conversation is returned.

Conversation list
GET /realtime/conversations

Returns data similar to:

[
  {
    "id": "conversation-uuid",
    "peer_id": "user-uuid",
    "peer_username": "alex",
    "unread_count": 2
  }
]
Message history
GET /realtime/conversations/{conversation_id}/messages
example response
{
  "items": [
    {
      "id": "message-uuid",
      "conversation_id": "conversation-uuid",
      "sender_id": "user-uuid",
      "body": "Hello",
      "created_at": "2026-10-22T13:30:00+00:00"
    }
  ],
  "next_cursor": "message-uuid"
}

The before query parameter can be used to load older messages:
GET /realtime/conversations/{id}/messages?before={message_id}&limit=50


2. WebSocket
The backend WebSocket endpoint is:

/ws


If the backend is running on port 8000, the frontend will connect using:


ws://localhost:8000/ws

For HTTPS production environments, it should use:
wss://your-domain.com/ws

The WebSocket implementation is in ws.py.


Authentication is handled using the existing session_id cookie in ws_auth.py.
The frontend must already be logged in. JavaScript does not need to manually read or send the cookie. The browser sends the cookie during the WebSocket handshake when the frontend and backend are correctly configured.

WebSocket message protocol
The protocol is defined in frames.py and documented in README.md.

Connecting
When the connection succeeds, the backend sends:

{
  "type": "ready",
  "user_id": "current-user-uuid",
  "username": "current-username"
}

The backend may then send:

{
  "type": "presence.snapshot",
  "online": ["user-uuid-1", "user-uuid-2"]
}

Sending a message
The frontend sends:
{
  "type": "message.send",
  "conversation_id": "conversation-uuid",
  "body": "Hello there"
}

The backend validates the conversation, saves the message, and sends this to the participants:

{
  "type": "message.new",
  "id": "message-uuid",
  "conversation_id": "conversation-uuid",
  "sender_id": "sender-uuid",
  "body": "Hello there",
  "created_at": "2026-10-22T13:35:00+00:00"
}

Receiving messages
If the recipient is connected, they receive the message.new frame immediately.

If the recipient is offline:

The backend stores a pending message.
The recipient connects later.
The backend sends the pending message.
The pending record is deleted after successful delivery.
This behavior is implemented in delivery.py and services/messages.py.

Read receipts
The frontend sends:

{
  "type": "read",
  "conversation_id": "conversation-uuid",
  "message_id": "message-uuid"
}
The backend sends a read receipt to the other participant:
{
  "type": "read",
  "user_id": "reader-uuid",
  "conversation_id": "conversation-uuid",
  "message_id": "message-uuid"
}
Presence
When a contact connects:
{
  "type": "presence",
  "user_id": "contact-uuid",
  "online": true
}

When the contact disconnects:

{
  "type": "presence",
  "user_id": "contact-uuid",
  "online": false
}

The backend tracks active sockets in memory through registry.py.

Ping and pong
The frontend can keep the connection alive by sending:
{
  "type": "ping"
}
The backend responds:
{
  "type": "pong"
}
The backend closes inactive sockets after approximately 45 seconds without activity.

How the integration should work
Step 1: Open the messages page
The page should first request:

The result should be converted into frontend contacts.

For each conversation, the frontend needs:

Conversation ID
Peer user ID
Peer username
Unread count
Online state
Message history

Step 2: Load the selected conversation history
When the user selects a conversation:
GET /realtime/conversations/{conversation_id}/messages

The frontend converts each backend message:
{
  id: backendMessage.id,
  sender: backendMessage.sender_id === currentUserId ? "me" : "them",
  text: backendMessage.body,
  time: formatDate(backendMessage.created_at)
}

The search page already has user IDs from /users.

  "peer_id": "selected-user-id"
}

Step 4: Open one shared WebSocket connection
The messages page or a shared private-layout provider should create:
const socket = new WebSocket("ws://localhost:8000/ws");



The connection should be created once, not every time the user changes conversations.

The frontend listens to socket.onmessage and handles:

ready
message.new
conversation.new
presence

read

notification.count

pong
Step 5: Send a live message
When the user submits the form, the frontend sends:

socket.send(
  JSON.stringify({
    type: "message.send",
    conversation_id: activeConversationId,
    body: messageInput.trim(),
  }),

The frontend should not immediately create a fake message with Date.now() as the ID. It should wait for the backend message.new event, because the backend provides the real message ID and timestamp.

When a message.new event arrives:

Find the conversation using conversation_id.
Convert the message into the UI format.
Add it to that conversation.
Update the last-message preview.
Increase the unread count if the conversation is not currently selected.
Automatically send a read frame if the conversation is currently open.

The UI components should not contain all WebSocket logic directly. Keeping it in a hook will be easier for a beginner to understand and prevents duplicated sockets.

Important backend considerations
Cookie authentication
The HTTP Axios client already uses:
withCredentials: true


For WebSockets, the browser handles the cookie during the connection handshake. The frontend must connect to the same backend host where the session cookie is valid.

Mutual-follow restriction
The backend currently prevents starting a new conversation unless both users follow each other.

This is enforced in conversations.py.

The frontend should display a clear error when the API returns 403.

UUIDs instead of numbers
The backend uses UUIDs for:

Users
Conversations
Messages
The current frontend uses numeric IDs in the messages UI. This must be changed before connecting the real API.

One socket per application session
The backend supports multiple sockets per user, but the frontend should normally use one shared connection for the private area. If each component opens its own socket, it can cause duplicate events and unnecessary connections.

Multiple backend workers
The backend registry is process-local. If the backend runs with multiple worker processes, a socket connected to worker A cannot directly deliver a live event through worker B.

For local development this is usually fine. Production would need Redis or another shared pub/sub system for reliable cross-worker realtime delivery.

Conclusion
The backend realtime feature is substantially implemented and has a clear protocol. The frontend is the missing part.

The safest integration order is:

Add accurate realtime TypeScript types.
Add Axios functions for conversations and message history.
Replace mocked contacts with /realtime/conversations.
Replace mocked messages with /realtime/conversations/{id}/messages.
Add a single shared WebSocket hook.
Handle message.new.
Connect message sending.
Add presence and read receipts.
Add notifications afterward.
So, yes, the frontend messaging UI can be connected to the backend without changing the backend protocol. The main work is replacing the mock state with HTTP data and adding one shared native browser WebSocket connection.
